# 因子值增量方案 v1（面向 P2 滚动训练）

> 目标：解决「当前仅有 2015-2025 大回测因子值」导致后续滚动训练不可持续的问题。  
> 适用：`qclaw_factor_engine` 与 `qclaw_strategy_engine` 当前 P1/P2 阶段。  
> 原则：先可用、可追溯、可回滚，再追求全自动。

---

## 1. 先给结论

- **必须做增量**：训练不能长期只依赖一次性全量 batch。  
- **推荐双轨**：`月度增量` + `季度/半年度全量重算（rebase）`。  
- **训练侧必须改规则**：读取因子值时用「**覆盖训练区间优先**」，不能只看最新 `created_at`。  
- **P1/P2 衔接**：P1 输出候选因子集合；P2 用同一锚点 `T` 读取覆盖 `[start_date, end_date]` 的因子值版本。

---

## 2. 现状问题定义

当前已知现状：

- 你已有一版大回测因子值（覆盖 `2015~2025`）。  
- P1 因子月监已跑通（DB 主链路 + `daily_csv` 对账）。  
- P2 正在启动（LightGBM 滚动训练）。

如果不做增量，风险如下：

1. 训练窗口向后滚动到 `2026+` 时，因子值会断档。  
2. 即便有新文件，若读取规则是「最新优先」，可能误读短区间文件。  
3. 无版本治理时，训练复现和审计困难（同一日期重跑结果不稳定）。

---

## 3. 方案总览（v1）

### 3.1 双轨策略

1. **月度增量（主线）**  
   每月锚点 `T` 跑一次增量，补齐上次 `date_end` 之后的新交易日因子值。

2. **定期重算 rebase（纠偏）**  
   每季度或半年，对关键 universe 跑一次较长区间全量（或半全量）重算，修正复权、数据修订、公式变更带来的漂移。

### 3.2 数据层语义（必须统一）

- `batch_csv`：训练/回测优先消费的批量因子值产物。  
- `daily_csv`：日更产物，优先用于执行与对账，不直接替代训练主数据（v1）。  
- `factor_value_files`：文件索引真源，训练必须通过该表解析文件路径与覆盖区间。
- `batch_id`：标识一次增量/重算批次（如 `inc_2026-05`、`rebase_2026Q2`）。  
- `stage`：发布阶段（`candidate` / `production` / `deprecated`）。  
- `is_rebase`：是否重算批次，用于训练读取优先级。

### 3.3 计算集合与训练集合解耦（必须）

- **增量计算集合**（因子工厂侧）和 **P2 训练集合**（策略侧）是两套集合，不能混用。  
- 增量计算集合用于「持续产出因子值底座」，目标是数据连续与可复用；训练集合用于模型效果与门禁。  
- v1 约定增量计算集合：  
  `incremental_compute_set = all_parsed_factor_ids - skip_factor_ids`  
  其中 `skip_factor_ids` 以 `factor_engine` 配置为准（当前 `config_dev.ini / config_sample.ini` 同名配置项）。  
- 若后续要省算力，再新增 v1-lite：  
  `(all_parsed_factor_ids - skip_factor_ids) ∩ is_valid_set`，但该模式会牺牲「失效因子复盘」连续性。

---

## 4. 月度增量流程（MVP）

### 4.1 输入

- 锚点日期 `T`（按 `calendar_policy` 对齐到交易日）。  
- 因子集合（**增量计算集合**）：`all_parsed_factor_ids - skip_factor_ids`（由 `factor_engine` 配置驱动，非 P2 训练集合）。  
- universe（当前默认 `ZZ500`，可扩展）。  
- 上一版已发布因子值区间（从 `factor_value_files` 查询）。

### 4.2 处理步骤

1. 查询每个因子当前 `production` 版本的 `date_end`（若尚未建立 stage 机制，临时回退到可用最新版本）。  

2. 计算增量区间：  
   `inc_start = last_date_end + 1 trading day`  
   `inc_end = T`

3. 预热回算（避免 rolling/REF 失真）：  
   真实计算区间使用 `inc_start - warmup_days` 到 `inc_end`，  
   输出落盘只保留 `inc_start ~ inc_end`。

4. 生成新的 `batch_csv`（或按现有产物规范），并写入 `factor_value_files` 索引记录（带 `date_start/date_end/batch_id/stage/is_rebase`）。

5. 生成批次清单（manifest），记录：批次 ID、因子数、失败因子、区间、生成时间、代码版本。

### 4.3 输出

- 新增 `batch_csv` 文件。  
- `factor_value_files` 新记录。  
- 批次 `manifest.json`（建议放在 `artifacts/factor_incremental/<batch_id>/`）。

---

## 5. 训练读取规则（核心约束）

P2 训练读取因子值时，规则必须是：

1. 先按 `factor_id + universe + artifact_type=batch_csv` 过滤。  
2. 取与训练区间有交集的记录：`date_end >= train_start AND date_start <= train_end`。  
3. 对同一因子按优先级排序：`is_rebase DESC, created_at DESC, id DESC`。  
4. 同一因子按排序结果做多文件拼接（重叠键 `trade_date+stock_code` 保留高优先级来源）。  
5. 拼接后裁剪到 `[train_start, train_end]`，并执行覆盖门禁。  
6. 将本次命中的 `batch_id` 集合写入训练 manifest。  
7. 若拼接后覆盖不足，**直接失败**（不要静默降级）。

> 说明：这条规则是本方案最关键的一条，确保“月增量 + rebase”可稳定拼接出训练窗。

---

## 6. 版本与状态治理（v1 简化）

建议先做最小状态治理（已落到 `factor_value_files` 字段）：

- 约定字段语义：`stage in {candidate, production, deprecated}`。  
- 训练读取优先使用区间相交 + 拼接，不强制单文件覆盖；重叠冲突按 `is_rebase > created_at > id`。  
- `batch_id` 用于跨系统追踪（增量任务、训练 manifest、发布记录三处一致）。  
- 每次切换生产版本，必须在 `notes.md` 记录：旧版本 -> 新版本、原因、日期、操作者。

---

## 7. 失败与回滚策略

### 7.1 失败策略

- 单因子增量失败：记录失败清单，批次标记 `partial_fail`，不自动提升生产。  
- 覆盖校验失败：阻断 P2 训练（明确报错缺哪段日期/哪类因子）。  
- 数据源异常：本批次不发布，沿用上一版 production。

### 7.2 回滚策略

- 生产版本切换仅通过「指针」或「状态位」完成。  
- 回滚=把指针切回上一个 production 批次，不删除历史文件。  
- 回滚动作需要留痕到 `docs/rollforward/notes.md`。

---

## 8. 与 P1 / P2 的衔接

### 8.1 P1 -> 增量

- 默认不强依赖 P1 结果，增量任务按「`all_parsed_factor_ids - skip_factor_ids`」持续计算，保证底座连续。  
- P1 结果可作为可选优化信号（例如二阶段补算或优先级调度），但不作为 v1 的硬门禁。

### 8.2 增量 -> P2

- P2 在训练开始前先做「覆盖区间校验」；  
- 训练 manifest 写明本次每个因子使用的版本来源（或至少写批次 ID 与区间）。

---

## 9. 实施顺序（建议）

1. **第 1 步**：落地独立编排入口 `src/factor_incremental/factor_incremental_runner.py`（结构解耦）。  
2. **第 2 步**：用增量模式跑月批（`mode=incremental`），写 `batch_id/is_rebase`。  
3. **第 3 步**：补充批次 manifest 与 notes 记录规范。  
4. **第 4 步**：训练侧固化读取规则为「覆盖优先 + rebase 优先」。  
5. **第 5 步**：再加季度 rebase 与更细的状态治理。

---

## 10. 验收清单（v1）

- [ ] 给定锚点 `T`，能产出本月增量因子值。  
- [ ] `factor_value_files` 能看到新增记录，`date_start/date_end` 正确。  
- [ ] P2 训练遇到覆盖不足会显式失败，不会偷偷降级。  
- [ ] 至少一次从 P1 -> 增量 -> P2 的串联演练跑通。  
- [ ] `notes.md` 有完整记录（批次 ID、区间、结果、是否发布）。

---

## 11. 当前默认参数（建议）

- `universe`: `ZZ500`  
- `warmup_trading_days`: `200`  
- 增量频率：月度（按锚点 `T`）  
- rebase 频率：季度（可按算力改半年）

---

## 12. 推荐入口（结构规范）

- 通用计算入口：`src/factor_engine/factor_engine_runner.py`（只负责算值与写库）。  
- 增量编排入口：`src/factor_incremental/factor_incremental_runner.py`（负责区间、warmup、批次、rebase 标识）。  
- 增量专用配置：`src/factor_incremental/config.ini`（开发环境自动切 `config_dev.ini`）。
