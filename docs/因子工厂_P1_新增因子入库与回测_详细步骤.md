# 因子工厂 P1：新增 MD 后的入库与回测（详细步骤）

> **仓库主责**：`qclaw_factor_engine`（本文档放在因子侧）。  
> **前置**：P0 已完成——根配置 `config.ini` / `config_dev.ini` 为唯一真源，详见根目录 `config_sample.ini` 与 `docs/config_keys_matrix.md`。  
> **与策略侧关系**：总优先级仍可与 `qclaw_strategy_engine/docs/rollforward/docs/滚动运营闭环_P0-P3_优先级总览.md` 对照阅读；**P1 实施细节以本文为准**。

---

## 1. P1 要解决的问题

| 问题 | 目标状态 |
|------|----------|
| 新增/变更因子 Markdown 后，流程不统一 | 固定一条可重复的「解析 → 登记 → 计算 → 回测 → 可查询结果」路径 |
| 全量大回测与「单因子试跑」混用 | 用**模式开关**和**任务队列语义**拆清 |
| 未来前端要「知道回测结果」 | 任务有 **job 标识 + 状态 + 结果摘要**（不依赖人看日志） |

---

## 2. 新增 MD 的三种方式与推荐触发

| 方式 | 说明 | 建议触发大回测的方式 | 原因 |
|------|------|----------------------|------|
| **(1) 站外抓取 + LLM 生成** | 批量、易失败、需去重/审核 | **异步批任务**（定时或手动触发一次 pipeline）；单因子成功后进入与 (2) 相同的「仅新因子」子流程 | 不适合 HTTP 长连接同步等完全库算完 |
| **(2) 纯 LLM 生成** | 与现有多半 CLI/服务类似 | **API/脚本 异步**：`POST` 返回 `job_id`，后台跑 `new_only` 管线 | 前端可轮询/SSE 查状态 |
| **(3) 手动编辑** | 人写 `factor_docs/md` | **保存后异步**同 (2)；若需要**秒级试算**可单独做 `quick` 子任务（见 §5） | 全量回测写库仍建议异步，避免阻塞 |

**统一原则**：

- **新增一条 MD** → 默认只触发 **「本因子 + 本批 factor_ids」** 的 `factor_engine` → `backtest_core` / `backtest_io` 最小闭环（与根配置中 `factor_ids` 或任务参数一致）。
- **全市场 / 全因子大回测** → 与「保存一篇 md」**解耦**，由 **周更脚本** 或显式 **「全量重跑」** 开关触发，避免每次点保存都算全库。

---

## 3. 回测模式开关（必做产品语义）

| 模式 | 配置/参数语义 | 典型场景 |
|------|----------------|----------|
| **`new_only` / 增量** | 本次只处理「本次事件关联的 `factor_id` 列表」（来自 md diff、上传列表或 job 入参） | 新 md、前端「保存并回测」 |
| **`full` / 全量** | 根配置中 `factor_ids` 留空＝全量，或分批评测 | 周更、`run_weekly_factor_pipeline` |
| **`revalidate`（可选）** | 指定 `factor_ids` 或 `universe` 上已 `is_valid` 子集 | 月监失败复检、阈值变更后重跑 |

**建议**：

- 默认前端的「保存/生成」只走 **`new_only`**。  
- 根配置与 CLI **显式**要求才能启动 **全量**（防误触）。

**实现落点**（与现有一致时最低改动）：

- 通过根 `config.ini` 的 `[factor_engine] factor_ids`、`[backtest] factor_ids` 或等价任务参数，只填本次 N 个 id；**不要**在「新因子事件」里改掉全量默认可跑全库的配置而不自知。

### 3.1 P1 首版与 P1 二版（准入）：分别做什么

> 把「**试跑有结果**」和「**按阈值改准入状态**」拆开，避免每次保存就动生产含义上的 `is_valid`。

| 版本 | 目标 | 典型步骤 | 是否动 `is_valid` / 多域 `factor_universe_status` | 是否跑 `selection_and_store` |
|------|------|----------|------------------------------------------------------|-----------------------------|
| **P1 首版** | 新因子/新 md 有**可查询**的试跑结果；前端能拿 `job_id` 看进度与摘要 | 解析 md → 登记 `factor_basic` / `factor_files` → `factor_engine` 写 **`factor_value_files`（batch_csv 等）** → `backtest_io` 写 **`factor_backtest` + 结果 JSON**；**默认单域**（根配置 `test_universe`） | **不自动改**；不在首版绑多域过阈 | **不跑**（除非你把首版范围刻意扩大，见下） |
| **P1 二版（准入 / governance）** | 在**已有**最新 `factor_backtest` 的前提下，按场景阈值**判定是否过线**，并**更新域状态/派生 is_valid** | 显式触发（按钮、单独 job、cron）：`selection_and_store` 读 **`factor_threshold_config`（按 `scene`）** → 更新 `factor_backtest.pass_standard`、**`factor_universe_status`（按域）** 及 **`factor_files` 指针** 等；与现网周更全链路一致 | **会**；与现网 `selection` 设计一致 | **跑** |

**二版要单独做的原因**：

1. `selection_and_store` 依赖 `factor_threshold_config` 中**激活的 scene** 与**最新** `factor_backtest` 行，和「第一次试跑可能不稳定」叠在一起容易误判。  
2. 改 `factor_universe_status` / 派生 `factor_basic.is_valid` 是**治理动作**，需要与「保存即试跑」在产品和权限上分离（人工确认或显式任务均可）。  
3. **多域**可在二版或**周更全量**中扩展，不必绑在首版每次保存上。

**折中**（若产品坚持「首版就要过线」）：仍建议 **同一条管线内顺序执行**，但在文档与 API 中拆为两个 **job 类型** 或两阶段 `run_mode`：`trial` 与 `selection_only`，且 `selection` 前校验 `factor_backtest` 已存在。

## 4. 与现有因子工厂主流程的对齐

当前主干（概念顺序）为：

1. `factor_docs` 解析出 `FactorDefinition`  
2. `factor_engine` 产出 `factor_value_files`（如 `batch_csv`）与落盘路径  
3. `backtest_core` + `backtest_io` → `factor_backtest` + 结果 JSON  
4. `selection_and_store` 按阈值更新 `is_valid` 等  
5. （周更）`factor_corr`、日更 `daily_factor_values` 等  

### 4.1 与现有业务表的关系（必读）

> 新拟表 **`factor_pipeline_job`** 只管「**这一次任务**」的状态与摘要；下面三张表是**现网业务数据**，P1 首版/二版与它们的触碰面不同。权威边界仍以 `docs/complete/db_conventions.md` 为准。

| 表 | 职责摘要 | 与 P1 首版 | 与 P1 二版（准入） |
|----|----------|------------|-------------------|
| **`factor_value_files`** | 按 `(factor_id, universe, artifact_type, …)` 存因子值产物的**权威相对路径**（如 `batch_csv`），供回测/策略侧选版 | **会写入/依赖**：`factor_engine` 产 batch_csv 后必须登记；`backtest_core`（`use_factor_value_files=true` 时）按此选路径。首版闭环**离不开**本表与磁盘一致。 | 二版不直接改本表；若重算后路径变更，以引擎/登记为准。 |
| **`factor_threshold_config`** | 分 **`scene`** 的 IC/换手等**阈值**与版本，供入库/复检等场景 | 首版**可不读**；若首版不跑 `selection` 则仅回测落库。 | **必读**：`selection_and_store` 用当前激活 `scene` 取阈值，判定 `pass_standard`。 |
| **`factor_universe_status`** | 因子在**各实证域**上是否**过线**等（与 `factor_basic.is_valid` 派生关系见库约定） | 首版**不依赖、不建议自动改**，避免与试跑强绑。 | **会更新**（通过 `selection_and_store` 与阈值判定，与现网周更链一致）。 |

**与 `factor_pipeline_job` 的分工**：

- **`factor_pipeline_job`**：给前端/运维「**这一单试跑/准入任务**成功了吗、错在哪、摘要 IC」——**过程态**。  
- **`factor_backtest` / `factor_value_files` / `factor_universe_status`**：给策略与因子库「**业务事实**」——**结果态**；**首版至少保证 `factor_backtest` + `factor_value_files` 与主链路一致。**

**P1 建议**：

- **新因子首跑（首版）**：做到 **(1)～(3)** 即视为「可验收闭环」；`factor_corr` 不必绑在每次保存上。  
- **状态可观测**：`factor_pipeline_job` 管任务态；**试跑成功**以 `factor_backtest` 行 +（可选）`result_summary` 为准。  
- **幂等**：相同 `factor_id` + 相同「逻辑版本/文档 hash」重复提交，应 **跳过或覆盖策略明确**，避免队列堆积。  
- **二版**单独排期或显式入口，与首版**解耦**（见 §3.1）。

**关联文档**（因子侧已存在、实施时交叉查阅）：

- `docs/complete/部署与自动化_日更与大回测.md`  
- `docs/complete/db_conventions.md`  
- `docs/config_keys_matrix.md`

## 5. 前端「及时反馈」：推荐交互（不绑具体框架）

1. 用户触发「生成/保存并回测」→ 服务创建 **任务记录**，返回 **`job_id`**。  
2. 后台跑：`parse` → `factor_engine`（仅 `factor_ids`）→ `backtest_io` 等。  
3. 前端用 **`GET /jobs/{job_id}` 轮询**，或 **WebSocket/SSE** 收 `status` + 摘要（IC、是否写库、错误信息）。  
4. 可选：增加 **`quick` 回测**（更短区间/单域）专供 UI 快反馈；**全区间正式结果**与夜间/异步任务 id 对齐。  

> 第一版可只用**轮询 + 数据库/文件状态**，不强制上 WS。

## 6. 分阶段实施步骤（建议严格按序；每阶段可验收后再进入下一阶段）

> 原则：**先数据与状态、再编排、再入口**；避免先写 runner 再补表导致返工。

---

### 阶段 A：业务规则定稿（不写代码、可 0.5～1 天）

| 步骤 | 内容 | 验收 |
|------|------|------|
| A1 | 画出 **任务状态机**（至少：`queued` → `running` → `success` / `failed`；是否允许 `cancelled`、失败是否可 `retry`） | 团队内能指着图说清每一种转移条件 |
| A2 | 定义 **幂等键**（推荐：`factor_id` + `doc_path` 的 hash 或 `factor_id` + `md5(文件内容)`），重复提交时的策略：`拒绝` / `合并为同一 job` / `覆盖重跑` 三选一写死 | 文档里一句话可执行 |
| A3 | 明确 **P1 最小闭环范围**：与 **§3.1 首版** 对齐（建议首版：`解析 md` → `factor_basic`/`factor_files` → `factor_engine` → 写 `factor_value_files` → `backtest_io` → `factor_backtest`；**二版/准入**再含 `selection_and_store` + `factor_threshold_config` / `factor_universe_status`） | 首版/二版边界无歧义 |
| A4 | （可选）定义 **quick** 与 **正式** 的差异：区间长短、`test_universe`、是否写 `factor_backtest` 全字段 | 配置或 job 参数能区分 |

**阶段 A 定稿（已确认：单人维护、内网使用）** — 可直接作为实现约定：

1. **状态机（最小集）**  
   - `queued` → `running` → `success` | `failed`  
   - 第一版**不做** `cancelled`（需要时再加）。  
   - `failed` **允许**用**新一次提交**重跑：产生**新的** `public_id`（新行），便于留审计；不强制在表内做 `retry_count`（以后可加）。

2. **幂等键 `idempotency_key` 与重复 `POST`（推荐行为）**  
   - 同一 `idempotency_key` 在目标 job 为 **`queued` / `running`**：再次 `POST` → **返回已有 `public_id` + 当前状态**（HTTP 用 **200**，语义为冪等，**不 409**），避免双点/重试/脚本并发造成第二条任务。  
   - 目标 job 为 **`success`**：再次 `POST` 同 key → **新建一条 job**（**新** `public_id`），表示「再跑一轮试跑」；若需「只查历史」应用 **`GET`**。  
   - 目标 job 为 **`failed`**：再次 `POST` 同 key → **新建一条 job**（新行），即**允许重试**；也允许**换新 key** 提交。  

3. **与「拒绝」策略的取舍**  
   - 内网、单人：优先 **冪等合并 + 失败可重跑**，**不**用「同 key 一律 409」挡请求，减少无效排障。

### 阶段 B：数据库表设计（先 Schema，再迁移脚本）

> 与 `docs/complete/db_conventions.md` 对齐：已有 `factor_basic` / `factor_files` / `factor_backtest` / `factor_candidate` 等；P1 **建议新增一张「任务表」** 专门承载 job 生命周期，避免把状态塞进未约定的列。

| 步骤 | 内容 | 验收 |
|------|------|------|
| B1 | 表名与职责定稿（建议名：`factor_pipeline_job`，仅存「一次管线执行」元数据） | 与现有表名风格一致（小写+下划线） |
| B2 | 编写 **字段草案**（见下 §6.1），与 DBA/自己评审：是否需要 `JSONB` 存 `result_summary`、是否要有 `created_by`（前端用户） | 评审通过 |
| B3 | 在 `sql/`（或你项目约定目录）新增 **建表迁移**（PostgreSQL）；本地/开发库执行成功 | `\d factor_pipeline_job` 结构正确 |
| B4 | （可选）为 `factor_candidate` 与 job 的关联：若候选因子先入 `factor_candidate`，再 job 转正，则补充外键或 `source_ref` 字段说明 | 文档补一句即可 |

#### 6.1 表结构草案：`factor_pipeline_job`（PostgreSQL，待你定稿后落地）

以下为 **实现前讨论稿**，字段名可微调，语义建议保留。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `BIGSERIAL` 主键 | 内部主键 |
| `public_id` | `UUID UNIQUE NOT NULL DEFAULT gen_random_uuid()` | 对外给前端的 `job_id`（也可用大写字符串，二选一） |
| `status` | `VARCHAR(32) NOT NULL` | `queued` / `running` / `success` / `failed`（或加 `cancelled`） |
| `source_type` | `VARCHAR(16) NOT NULL` | 与 §2 对应：`crawl` / `llm` / `manual`（或数字 1/2/3） |
| `run_mode` | `VARCHAR(32) NOT NULL` | `new_only` / `full` / `revalidate` / `quick` |
| `factor_ids` | `TEXT NOT NULL` | 逗号分隔或 JSON 数组字符串（若用 JSONB 更优可改） |
| `test_universe` | `VARCHAR(32)` | 本次实证域；可空则读根配置 |
| `idempotency_key` | `VARCHAR(128) UNIQUE` | 防重复提交；可空 |
| `error_message` | `TEXT` | 失败时人类可读原因 |
| `result_summary` | `JSONB` | 成功时摘要：如 `ic_value`、`result_json_rel_path`、`factor_backtest.id` 列表等 |
| `log_rel_path` | `VARCHAR(512)` | 可选：关联一次 run 的日志相对路径 |
| `created_at` | `TIMESTAMPTZ DEFAULT now()` | 创建时间 |
| `started_at` | `TIMESTAMPTZ` | 开始执行时间 |
| `finished_at` | `TIMESTAMPTZ` | 结束时间 |

**索引建议**：`(status, created_at)`；`idempotency_key` 唯一（已上表）。

### 阶段 D：编排层（Worker / 子进程调用现有脚本）

| 步骤 | 内容 | 验收 |
|------|------|------|
| D1 | 实现「从 `queued` 取 job」的 **单 worker**（进程内循环或 cron 每分钟一次即可） | 不依赖重型消息队列也可 |
| D2 | `running` 时按 `run_mode` 生成 **临时 ini 片段** 或 **环境变量覆盖**，只填本次 `factor_ids`，调用现有： `factor_engine_runner` → `backtest_io_runner`（顺序与周更文档一致） | 与根配置**不互相覆盖文件**（临时文件或子配置） |
| D3 | 每步结束更新 `result_summary` 或失败写 `error_message`；最后 `success`/`failed` + `finished_at` | 库中 job 行状态正确 |
| D4 | **全量防护**：`run_mode=full` 必须显式来源（如仅 CLI、`ENV=ALLOW_FULL=1`），禁止普通「保存 md」默认走 full | 误触全量不可达 |

**已落地（首版 worker，供体验 D1～D3 + D4）**：

- 代码：**`src/pipeline_job_worker/worker.py`**、根目录 **`run_pipeline_job_worker.py`**；库表方法 **`src/pipeline_job_api/job_store.py`** 中 `claim_next_queued` / `mark_job_success` / `mark_job_failed`。  
- 行为：``FOR UPDATE SKIP LOCKED`` 领取 `queued` → 置 `running`；`run_mode in {new_only, quick, trial, revalidate, full}` 走 `run_factor_engine(...)` → `run_backtest_io(...)`；`run_mode=selection_only` 仅执行 `selection_and_store`（不包含 `new_only` 计算阶段）→ `success` 写 `result_summary` 或 `failed` 写 `error_message`。`run_mode=full` 需 **`ALLOW_FULL=1`** 与 API 一致。  
- 不依赖临时 ini：与 factor_engine / backtest_io 已实现的**参数覆写**一致（见 D2 原可选项）。详细命令见 **`docs/因子工厂_P1_pipeline_job_API_使用步骤.md`「十、Pipeline job worker」**。
