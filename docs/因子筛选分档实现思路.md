# 因子筛选分档实现思路（低档 / 中档 / 高档）

> 目的：把「私募式因子月审」（多窗 IC、连续失效、分层池、组合收益等）拆成可落地的三档，便于排期与控范围。  
> 现状锚点：`src/factor_monitor/` 月监（截面 IC + 覆盖率、阈值 `factor_threshold_config`、候选来自 `factor_universe_status.is_valid`、报告落盘 JSON/MD、**默认不写回** `is_valid`）。

---

## 0. 三档对照（一句话）

| 档位 | 目标 | 大致体量（经验值） |
|------|------|-------------------|
| **低档** | 报告更像「月审」：多窗指标 + 基于历史报告的连续失效提示 | 约 1～3 人日起（视历史存储约定） |
| **中档** | 接近文章规则：组合层收益 + 池子分层状态与变更流程 | 约 1～2 周起（视组合口径与 DB 变更范围） |
| **高档** | 与训练/回测/风控同源、自动化闭环 | 持续迭代型项目 |

---

## 1. 低档：报告增强 + 运维可读（不改池、不强绑模型）

### 1.1 实现思路

- **复用**现有按日截面算 IC 的路径（`factor_monitor_runner` 内对 `monitor_window` 的 panel）。
- **扩展**：在同一批因子上，对 **多个日历窗**（或固定交易日长度：如 20 / 60 / 120 日）分别汇总 `ic_mean`、`ic_ir`、`coverage_mean`，写入 JSON/MD 并列字段（如 `windows: { "20d": {...}, "60d": {...}, "120d": {...} }`）。
- **连续 N 月失效**：不强制先上 DB；约定 **历史月报落盘路径**（例如 `artifacts/factor_monitor/YYYY-MM/factor_health_*.json`），月跑结束时 **读取最近 K 份**同 universe 报告，按 `factor_id` 统计连续 `FAIL` 次数，输出 `streak_fail_months` 与「建议复核」列表（仍为 **建议**，不写 `is_valid`）。

### 1.2 推荐步骤

1. **口径冻结**：与策略侧文档对齐「1M/3M/6M」用自然月还是 rolling 交易日；建议第一版用 **rolling 交易日**（实现简单、可复现）。
2. **数据**：确认 `monitor_window_days`、`warmup_trading_days` 能覆盖最长窗口（例如 120 日 + 缓冲）。
3. **代码**：在单因子指标计算后，按多个 `(start, end)` 子窗切片复算聚合；阈值可共用同一 `scene` 或按窗配置不同 scene（第二版）。
4. **连续失效**：定义「一月一次」的 `as_of_date` 与文件命名；实现小模块 `load_last_k_reports(universe, k)` + 合并逻辑。
5. **报告**：MD 增加「多窗摘要表」「连续 FAIL ≥N 清单」；JSON 保持结构化便于后续入库。
6. **验收**：指定历史三个月手工对照若干因子 IC 符号与量级；连续失效与人工数 FAIL 次数一致。

### 1.3 依赖与风险

- **依赖**：磁盘上可追溯的历史 JSON（或日后改读对象存储同路径约定）。
- **风险**：窗口边界与节假日导致「月」与「20 交易日」语义不一致——必须在报告头写清 **本次使用的窗定义**。

## 2. 中档：组合收益 + 池子分层（进入「制度 + 数据」）

### 2.1 实现思路

- **组合层**：在 ZZ500（或当前 `universe`）截面上，按因子分位数 **分组**（如 quintile），构造 **多头（top）/空头（bottom）** 或多空价差，用与月监一致的 **前向收益 label**（与现有 `fwd_ret` horizon 对齐）算窗口内 **累计收益、波动、夏普近似**；可选简化：等权、不考虑交易成本（首版在报告中 **显式声明**）。
- **池子分层**：引入稳定 **枚举**（如 `CORE` / `WATCH` / `DROP_CANDIDATE`），存放位置二选一或组合：  
  - **扩表**：`factor_universe_status` 增加 `pool_tier`、`tier_changed_at`、`tier_reason`；或  
  - **新表**：`factor_pool_history(factor_id, universe, tier, effective_date, operator, reason_json)` 做审计。  
  **月监任务**：根据规则 **计算目标 tier**，再通过 **独立审批流或人工脚本** 写库（避免单次 FAIL 直接删核）。
- **规则示例**（需产品拍板）：多窗 ICIR 同时满足 → 可标 `CORE` 候选；连续 N 月 FAIL → `DROP_CANDIDATE`；中间 `WATCH`。

### 2.2 推荐步骤

1. **组合口径文档**：权重（等权 / 指数权重）、是否剔除 ST/停牌、是否 winsorize 收益；与 `label_ic_convention` 一致。
2. **原型**：单因子、单日截面 → 扩展到全窗口序列 → 再批量因子。
3. **性能**：ZZ500 × 全因子 × 多日，注意向量化与缓存行情；必要时只对 `WATCH` 与边界因子算组合层。
4. **DB 迁移**：迁移脚本 + `db_conventions` 补充字段说明；策略/训练侧读 tier 的 **单一数据源** 约定。
5. **写回策略**：默认「只算建议 tier」，**人工或审批 job** 落库；可选 `--apply-tier` 开关仅限运维角色。
6. **验收**：与现有大回测或手工 Excel 对几条因子的多空曲线形状（不必逐点相等，但符号与极端日期可解释）。

### 2.3 依赖与风险

- **依赖**：DB 变更权限、与策略工厂用因子列表的 **同步契约**。
- **风险**：组合收益与 IC 结论冲突时的 **仲裁规则**；避免「月监 FAIL 但组合赚」无文档解释。

## 3. 高档：与回测 / 训练 / 风控同源闭环

### 3.1 实现思路

- **标签与成本同源**：月监、大回测、LGBM 训练使用 **同一套** label 定义、调仓频率、费率、中性化层级（行业/市值等）。
- **风格与风险**：因子暴露序列对接 **风险模型或 Barra 类约束**；「观察池」因子仅允许 **受限暴露** 进入组合优化。
- **自动化**：月报 → 自动开 ticket → 审批 → 更新池子 → 下游日更/训练配置 **版本化**（config hash + 数据快照指针）。
- **监控与回放**：任意实盘日可回放「当时若按规则应处于哪一 tier」，满足合规与复盘。

### 3.2 推荐步骤（粗粒度）

1. 统一 **因子与标签 master 配置**（单 repo 或单注册表）。  
2. 大回测与 `factor_monitor` **共享库函数**（避免两套 forward return）。  
3. 训练管线读取 **pool_tier**，过滤或降权；CI 中加「tier 变更后训练可复现」检查。  
4. 实盘风控校验 **实际暴露 vs 允许暴露**。  
5. 文档化 **发布清单**（与策略引擎 rollforward 文档联动）。

### 3.3 依赖与风险

- **依赖**：跨仓库（factor_engine / strategy_engine / 数据层）排期与 owner。  
- **风险**：过度自动化导致「静默改池」——必须有审计与回滚。

---

## 4. 建议演进顺序（实操）

1. **先做低档**：多窗 + 连续 FAIL 提示，成本低且立刻提升报告决策价值。  
2. **再做中档中的「组合收益（只读）」**：仍不写 tier，避免流程未就绪就改库。  
3. **最后上 tier 写库 + 高档同源**：在低档/中档指标稳定、团队对口径无异议后推进。
