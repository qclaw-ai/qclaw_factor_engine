# 因子工厂 P1：增量编排与前端任务隔离修正步骤

> 目标：避免前端试跑（尤其 quick/trial）污染增量编排的 `last_end_date` 计算，保证日常增量链路稳定。  
> 结论：采用**关键隔离规则 #1** —— 以 `factor_value_files.stage` 做筛选隔离（不改核心表结构）。

---

## 1. 问题与修正目标

当前增量编排 `factor_incremental_runner` 通过 `factor_value_files` 取最大 `date_end` 作为下一次起点。  
如果前端试跑任务写入了短窗口结果，且未隔离 stage，可能导致：

- 增量起点漂移（跑快窗后被当成主链最新）；
- 新增因子未建立基线时就进入增量，产生时间线断裂；
- 回测结果看起来“成功”，但生产链路水位不可信。

修正目标：

1. 前端任务可继续产出可视化结果；
2. 增量链路只认“主链可用 stage”的因子值；
3. 新增因子未建基线时不误入增量主链。

---

## 2. 关键隔离规则（采用方案 #1）

按 `factor_value_files.stage` 隔离：

- **前端试跑类任务**：写 `stage=trial`（或 `quick`，建议统一为 `trial`）；
- **主链可用产物**：`stage in ('candidate', 'production')`；
- **增量起点查询**：仅在 `stage in ('candidate', 'production')` 范围内取 `MAX(date_end)`。

这样不需要新增水位表，也不需要改 `factor_value_files` 主键结构，改动最小。

> 注意：**即使前端暂时不做 quick，也建议保留该隔离**。  
> 原因是污染来源不只 quick：`new_only` 临时重跑、脚本回放、手工任务同样可能写入 `factor_value_files`，进而影响增量 `MAX(date_end)` 语义。

---

## 3. 前端任务与 stage 约定（直接回答）

### 3.1 前端新增因子，如果不选 quick，能不能写 `candidate` / `production`？

**可以，但建议默认只写 `candidate`，不要直接写 `production`。**

推荐规则：

- `quick=true` 或 `run_mode in ('quick', 'trial')` -> `stage='trial'`
- `run_mode='new_only'`（前端默认首跑） -> `stage='candidate'`
- `run_mode='full'`（显式、受控） -> 可写 `stage='production'`（或由审批后再升）

原因：`production` 代表可进入主链增量的“可用基线/版本”，不应由普通前端首跑直接赋值。

### 3.3 前端是否开放 `run_mode=full`？

**建议：默认不开放给普通前端用户。**

仅在受控入口（管理员/运维）开放，并要求：

1. 权限校验（RBAC：admin）；
2. 二次确认（明确提示资源消耗与影响范围）；
3. 保留现有后端防护（`X-Allow-Full-Run: 1` / `ALLOW_FULL=1`）；
4. 并发限制（同一时刻最多 1 个 full）。

原因：`full` 是基线重建/回归验证类操作，成本高且对主链影响大，不适合作为普通提交流程按钮。

### 3.2 新增因子尚未大回测（基线）就触发增量怎么办？

建议行为：

- 增量编排检测到该因子无 `candidate/production` 有效记录时：**跳过并记录告警**；
- 可选：自动创建一条 `baseline/full` job（后续迭代）。

---

## 4. 代码改动步骤（按顺序）

### 步骤 A：统一 stage 映射（worker 侧）

在 `pipeline_job_worker` 里按 `run_mode` 映射 `stage_override` 传给 `run_factor_engine`：

- quick/trial -> `trial`
- new_only/revalidate -> `candidate`
- full -> `production`（前提 `ALLOW_FULL=1`）

> 不要删除现有 `stage_override` 参数，保持兼容。

### 步骤 B：增量起点查询增加 stage 过滤

在 `factor_incremental_runner.py` 的 `_get_last_batch_end_date` SQL 中增加：

- `stage IN ('candidate','production')`
- 保留 `artifact_type='batch_csv'` 与 `universe` 条件。

### 步骤 C：未建基线因子处理

当 `_get_last_batch_end_date` 返回空时：

- 对历史已运行因子可回退 `base_start_date`（现有行为）；
- 对“新增因子首跑且无主链 stage”建议打明确日志：`missing_baseline`；
- 建议将该因子留在 candidate 流程，不直接进入 production 增量。

### 步骤 D：日志与可观测性

必须补日志：

- worker 执行时打印 `run_mode -> stage` 映射；
- 增量计算起点时打印 `universe`、`allowed_stages`、`last_end_date`；
- 若回退到 `base_start_date`，打印原因（无主链 stage 记录）。

---

## 5. SQL / 查询口径示例

> 以下仅示意查询口径，实际以代码内 SQL 为准。

```sql
SELECT MAX(date_end) AS max_date_end
FROM factor_value_files
WHERE universe = :universe
  AND artifact_type = 'batch_csv'
  AND stage IN ('candidate', 'production');
```

## 6. 验证清单（必须过）

1. 提交 quick/trial 任务后，`factor_value_files.stage='trial'`；
2. 增量 runner 日志显示仅按 `candidate/production` 取 `MAX(date_end)`；
3. 即便存在更新更晚的 `trial` 记录，增量起点不受影响；
4. 新增因子未建主链基线时，不会错误推进 production 增量；
5. 前端 `job_id/result` 仍可正常查看回测结果（不受 stage 隔离影响）。

---

## 7. 风险与后续建议

- 当前采用 stage 过滤，依赖 stage 写入正确；若有历史脏数据，需要一次修复脚本。
- 后续若链路更复杂，可升级为“独立增量水位表”（每因子每域维护 last_end_date），彻底与产物表解耦。
