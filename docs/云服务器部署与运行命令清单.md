# 云服务器部署与运行命令清单（JQ 版：2015-至今分批 + 周增量 + Parquet 外发）

> 适用仓库：`qclaw_factor_engine`  
> 目标：在云服务器上部署后，从 0 跑到可对外交付（factor + label 的 Parquet + meta），并形成可长期运维的日常节奏。  
你当前约束：

- **行情来源**：仅聚宽（JQ）
- **stock_daily**：2015-至今，允许分批（建议 4~5 年一批）
- **首次全量因子值**：`src/factor_engine/factor_engine_runner.py`
- **后续增量**：`src/factor_incremental/factor_incremental_runner.py`（建议周跑）
- **对外交付**：COS + Parquet（月分区 + manifest/watermark）

---

## 0. 目录与约定

- **仓库目录**（示例）：`/data/qclaw/qclaw_factor_engine`  
- **生产配置文件**：仓库根 `config.ini`（建议不要用 `config_dev.ini` 跑生产）  
- **Python 运行时**：Miniconda（你选择直接使用 **base 环境**）  
- **解释器路径**：`/home/ubuntu/miniconda3/bin/python`  
- **对外 Parquet 输出根**（默认）：`artifacts/factor_export_parquet/`

---

## 0.1 执行入口说明（py / sh 哪个该用）

本仓库支持两类运行入口：

- **直接跑 Python（.py）**：适合一次性初始化、单步排障、手动回放某个环节。
- **跑 `bin/*.sh`**：适合长期线上 cron（统一日志、统一 `PYTHON_BIN/ENV/PYTHONPATH`，少踩 cron 环境坑）。

对照表（本文后续每一步也会再次标注）：

| 场景 | 推荐入口 | 说明 |
| --- | --- | --- |
| **全量灌库 stock_daily**（2015-至今分批） | **只能 py** | 当前没有对应的 `bin/*.sh` 包装；建议手动分批跑 `data_ingest_stock_daily_jq_initial.py` |
| **每天全链路（最新数据）** | **sh** | 用 `bin/run_daily_full_pipeline.sh`：行情同步 + 日更 bundle + **daily→yearly merge** + Parquet 导出/校验 +（可选）COS 上传 |
| **仅跑“日内因子线”** | **sh 或 py** | `bin/run_daily_factor_pipeline.sh`（含 merge）或分别跑 `daily_stock_and_calendar_sync.py` / `daily_factor_values_runner.py` / `daily_parquet_merge_to_yearly_runner.py` |
| **仅跑“Parquet 外发”（factor+label+校验）** | **sh 或 py** | `bin/run_daily_parquet_export_pipeline.sh` 或分别调用导出/校验 .py |
| **历史 Parquet 回填（按月）** | **sh 或 py** | `bin/run_monthly_parquet_backfill.sh` 或分别跑两个 bootstrap .py |
| **同步 COS** | **sh（推荐）或 py** | `bin/run_cos_upload_daily.sh` / `bin/run_cos_upload_full.sh`（内部会调用 python SDK 脚本） |

## 1. 一次性准备：代码 + Python 环境

你使用 **Miniconda base 环境**（路径：`/home/ubuntu/miniconda3/bin/python`）。

在云服务器上执行（示例路径，自行替换）：

```bash
cd /data/qclaw/qclaw_factor_engine
```

## 4. 第一步：全量灌库 `stock_daily`（2015-至今，4~5 年一批）

入口选择：

- **只能 py**：当前未提供对应 `bin/*.sh`。

脚本：`src/data_ingest/data_ingest_stock_daily_jq_initial.py`  
作用：从聚宽拉历史日线，upsert 写入 `stock_daily`。

### 4.1 建议分批区间（示例）

- 批次 1：2015-01-01 ~ 2019-12-31  
- 批次 2：2020-01-01 ~ 2024-12-31  
- 批次 3：2025-01-01 ~ 今日

### 4.2 每批执行方式

做法：每次在 `config.ini` 的 `[data_ingest_jq_initial]` 填 `start_date/end_date/universe`，然后跑脚本：

```bash
/home/ubuntu/miniconda3/bin/python src/data_ingest/data_ingest_stock_daily_jq_initial.py
```

### 4.3 验收（抽检）

- DB 表 `stock_daily` 在目标区间有数据  
- `PRIMARY KEY (trade_date, stock_code)` 无冲突  
- 取少量股票检查 OHLCV 值是否为合理数值

## 6. 第三步：首次全量生成因子值 Parquet（按区间分批，写入 `factor_value_files`）

入口选择：

- **推荐 py**：首次全量建议你手动按 4~5 年分批跑 `factor_engine_runner.py`，便于中断/重跑与定位问题。
- **可选 sh**：`bin/run_weekly_factor_incremental_pipeline.sh` 只跑 `factor_incremental_runner` → `factor_engine_runner`（**yearly_parquet** 主链路）；首次全量仍建议手跑 `factor_engine_runner.py` 分批窗口，便于中断/重跑。

建议在首次全量跑因子前，先把 md 元信息写入 `factor_basic`（避免 `factor_value_files` 外键问题）：

```bash
/home/ubuntu/miniconda3/bin/python scripts/bootstrap_factor_basic_from_docs.py --config config.ini
```

脚本：`src/factor_engine/factor_engine_runner.py`  
作用：

- 计算因子值并按年写入 **`factor_values_parquet/yearly/by_universe/{UNIVERSE}/{factor_id}/{factor_id}-{year}.parquet`**
- 写入 DB 表 `factor_value_files`（**`artifact_type=yearly_parquet`**，按年单行覆盖）

### 6.1 建议分批（示例：ZZ500）

> 说明：你对外当前主域是 `ZZ500`，建议首次全量就先把 `ZZ500` 打通并稳定交付；后续再扩 `HS300`。

```bash
/home/ubuntu/miniconda3/bin/python src/factor_engine/factor_engine_runner.py --config config.ini --start-date 2015-01-01 --end-date 2019-12-31 --universe ZZ500 --batch-id rebase_2015_2019
/home/ubuntu/miniconda3/bin/python src/factor_engine/factor_engine_runner.py --config config.ini --start-date 2020-01-01 --end-date 2024-12-31 --universe ZZ500 --batch-id rebase_2020_2024
/home/ubuntu/miniconda3/bin/python src/factor_engine/factor_engine_runner.py --config config.ini --start-date 2025-01-01 --end-date 2025-12-31 --universe ZZ500 --batch-id rebase_2025
```

> `batch_id` 建议从第一天开始就带上，便于追溯与冲突治理（rebase/增量）。

### 6.2 验收

- 目录 `factor_values_parquet/yearly/by_universe/ZZ500/` 下存在各 `factor_id` 的 `*.parquet`  
- DB 表 `factor_value_files` 中存在 **`artifact_type=yearly_parquet`** 的登记记录（含 `year/rel_path/date_start/date_end/stage/batch_id` 等）

## 8. 日更因子 bundle + 回补年度（`factor_export` 的 `--include-daily` 依赖磁盘 daily）

入口选择：

- **推荐 sh**：`bin/run_daily_full_pipeline.sh` 或 `bin/run_daily_factor_pipeline.sh`（含：`daily_stock_and_calendar_sync` → `daily_factor_values_runner` → **`daily_parquet_merge_to_yearly_runner`**）
- **也可 py**：按顺序分别跑上述三个脚本（merge 可单独重跑，无需重算日更）

脚本：`src/daily_factor_values/daily_factor_values_runner.py`  
作用：写 **`factor_values_parquet/daily/by_universe/{UNIVERSE}/{T}/factors.parquet`** + `manifest.json`（不落逐因子 CSV）。

脚本：`src/daily_factor_values/daily_parquet_merge_to_yearly_runner.py`  
作用：把当日 bundle 合并进 **`yearly_parquet`** 文件并 upsert `factor_value_files`（导出主读 yearly）。

示例：

```bash
/home/ubuntu/miniconda3/bin/python src/daily_factor_values/daily_factor_values_runner.py --config config.ini --trade-date 2026-04-28 --universe ZZ500 --scope all_in_basic
/home/ubuntu/miniconda3/bin/python src/daily_factor_values/daily_parquet_merge_to_yearly_runner.py --config config.ini --universe ZZ500 --trade-date 2026-04-28
```

> `factor_export_runner.py --include-daily` 读的是磁盘上的 **daily bundle（Parquet）**，不要求 `artifact_type=daily_csv` 索引。

## 10. 第六步：同步到 COS（对外下载）

入口选择：

- **推荐 sh**：
  - `bin/run_cos_upload_daily.sh`（每日增量）
  - `bin/run_cos_upload_full.sh`（全量）
- **也可 py**：直接运行 `scripts/upload_factor_export_parquet_daily.py` / `scripts/upload_factor_export_parquet_full.py`

原则：把 `artifacts/factor_export_parquet/` **原样**同步到 COS 指定前缀，保持目录结构不变（客户才能按 manifest 直接下载）。

当前已提供 **COS SDK（内网 endpoint）上传脚本 + sh 入口**：

- 全量上传（首次历史回填后用）：
  - `bin/run_cos_upload_full.sh`（内部调用 `scripts/upload_factor_export_parquet_full.py`）
- 每日增量上传（每天跑完导出后用）：
  - `bin/run_cos_upload_daily.sh`（内部调用 `scripts/upload_factor_export_parquet_daily.py`）

配置方式：

- 你可以直接在 `bin/run_cos_upload_*.sh` 里填写 `COS_SECRET_ID/COS_SECRET_KEY`（你已明确要这么做，注意别提交到 git）
- 或通过环境变量 / `COS_ENV_FILE` 注入（更稳）

详细用法见：`docs/COS同步_使用说明.md`

同步验收：

- COS 上能访问 `meta/watermark/factor/ZZ500.json`、`meta/manifest/factor/ZZ500/2026-04.json`  
- 客户端可按 `manifest.part_rel_paths` 下载 `part-*.parquet`

## 11. 建议的定时任务（最小可运维版本）

> 时间点按你收盘后可用时间调整，这里给一套“够稳、够省心”的默认节奏。

### 11.1 每天（交易日）

- 20:10 同步 `stock_daily + calendar`  
  - `daily_stock_and_calendar_sync.py --lookback-days 15`
- 21:10 日更 bundle + **merge→yearly**（`run_daily_factor_pipeline.sh` 已包含；若用 `--include-daily` 导出则必须有磁盘 daily + 已 merge 的 yearly 更稳）  
  - 等价拆分：`daily_factor_values_runner.py` → `daily_parquet_merge_to_yearly_runner.py`
- 21:40 导出当月 Parquet（factor + label）并校验  
  - `python src/factor_export_cos/factor_export_runner.py --month 当月` + validate  
  - `python src/factor_export_cos/label_export_runner.py --month 当月` + validate  
- 22:30 同步 COS（如果对外）

### 11.3 cron（建议写法：直接用 base python 绝对路径）

推荐方式：**每天只跑一个入口脚本** `bin/run_daily_full_pipeline.sh`，它会完成：

- 行情同步 + 日更 bundle + **daily→yearly merge**（`bin/run_daily_factor_pipeline.sh`）
- 导出当月 factor+label Parquet + validate（`bin/run_daily_parquet_export_pipeline.sh`）
- 可选：SDK 上传 COS（`bin/run_cos_upload_daily.sh`，通过 `ENABLE_COS_UPLOAD=1` 开启）

示例（每天 21:10 跑全链路；工作日示例，你也可以改成交易日调度）：

```cron
ENV=prod
PYTHON_BIN=/home/ubuntu/miniconda3/bin/python
UNIVERSE=ZZ500
CONFIG_FILE=config.ini
ENABLE_COS_UPLOAD=1
10 21 * * 1-5 /data/qclaw/qclaw_factor_engine/bin/run_daily_full_pipeline.sh
```

### 11.4 建议新增的 bin 入口（替代直接跑 .py）

你可以把“对外 Parquet 导出/回填/COS 同步”也统一走 `bin/*.sh`：

- `bin/run_daily_parquet_export_pipeline.sh`：每天导出当月 factor+label Parquet + validate
- `bin/run_daily_full_pipeline.sh`：每天全链路（行情同步+日更因子+Parquet 外发+校验+可选 COS 同步）
- `bin/run_monthly_parquet_backfill.sh`：按月区间回填 factor+label Parquet（首次回填/重跑失败月）
- `bin/run_cos_upload_daily.sh`：SDK 每日增量上传（本月 parts + manifest + watermark）
- `bin/run_cos_upload_full.sh`：SDK 全量上传（首次历史回填后用）
- `bin/run_cos_sync_factor_export_parquet.sh`：通用同步壳（适合 coscmd/rclone；可选）

### 11.2 每周（周日凌晨）

- 03:00 跑增量编排：`bin/run_weekly_factor_incremental_pipeline.sh`（或 `factor_incremental_runner.py`）

## 13. 新增因子上线 SOP（新增因子后如何让客户拿到数据）

> 目标：新增因子后，保证：
>
> - 云端日常链路继续稳定（daily full pipeline + parquet + COS）
> - 客户能拿到新增因子列（默认要求：补全历史；不再支持“只从今天开始”作为上线口径）

### 13.1 前置：新增因子进入可计算集合

入口选择：**py（必要时）**

检查点：

- 新因子文档已放入 `factor_docs/md/`（或你的 `[paths].factor_docs_dir` 指向的目录）
- `factor_engine_runner.py` 能解析出该 `factor_id`（本地/云端可先小窗口试跑）

建议先做最小联调（不跑全量，避免一上来就长跑）：

```bash
/home/ubuntu/miniconda3/bin/python src/factor_engine/factor_engine_runner.py --config config.ini --start-date 2026-04-01 --end-date 2026-04-05 --universe ZZ500 --factor-ids <NEW_FACTOR_ID>
```

验收：

- `factor_values_parquet/yearly/by_universe/ZZ500/<NEW_FACTOR_ID>/` 下出现对应 **`{factor_id}-{year}.parquet`**
- DB 表 `factor_value_files` 出现该因子的 **`yearly_parquet`** 登记记录（按年）；日更链路只补充近日截面，不替代首次区间批量

### 13.2 默认路线：补全历史（4~5 年一批分批补）

入口选择：**py（推荐） + sh（导出/上传）**

步骤 1：按 4~5 年分批跑历史 **yearly_parquet**（只跑新增因子）

示例（ZZ500）：

```bash
/home/ubuntu/miniconda3/bin/python src/factor_engine/factor_engine_runner.py --config config.ini --start-date 2015-01-01 --end-date 2019-12-31 --universe ZZ500 --batch-id rebase_<NEW_FACTOR_ID>_2015_2019 --factor-ids <NEW_FACTOR_ID>
/home/ubuntu/miniconda3/bin/python src/factor_engine/factor_engine_runner.py --config config.ini --start-date 2020-01-01 --end-date 2024-12-31 --universe ZZ500 --batch-id rebase_<NEW_FACTOR_ID>_2020_2024 --factor-ids <NEW_FACTOR_ID>
/home/ubuntu/miniconda3/bin/python src/factor_engine/factor_engine_runner.py --config config.ini --start-date 2025-01-01 --end-date 2025-12-31 --universe ZZ500 --batch-id rebase_<NEW_FACTOR_ID>_2025 --factor-ids <NEW_FACTOR_ID>
```

验收：

- `factor_value_files` 中该因子有对应各年的 **`yearly_parquet`** 记录（`year` + `date_start/date_end` 与区间一致）

步骤 2：回填 Parquet（只需要重建受影响的月份）

你可以：

- 小范围：只重跑某几个月（手动调用 `python src/factor_export_cos/factor_export_runner.py --month ...`）
- 大范围：直接用按月回填脚本跑一段月份区间：

```bash
UNIVERSE=ZZ500 START_MONTH=2015-01 END_MONTH=2025-12 /data/qclaw/qclaw_factor_engine/bin/run_monthly_parquet_backfill.sh
```

> 说明：回填脚本会跑 factor+label；如果你只想重建 factor，可以临时改用 python 只跑 factor 的 bootstrap（或后续我们再加一个“只回填 factor”的 sh）。

步骤 3：同步 COS

- 如果你是“少量月份重建”：建议当天跑完导出后用 `bin/run_cos_upload_daily.sh` 推本月即可
